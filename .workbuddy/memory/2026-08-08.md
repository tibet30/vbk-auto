## AI 产品生成提示词重构

用户反馈 AI 生成产品时返回的 JSON 经常缺失字段。分析发现提示词/JSON Schema 存在结构性缺陷，根源在于 `value: {}` 不给嵌套结构约束，以及 presentation/itinerary/terms 等复杂路径的子字段从未在 prompt 中明确列出。

### 改动文件
`src/main/minimax/minimax-constants.ts` — 4 处改动：

1. **`writablePatchGuide`** — 从混杂约束改为清晰的白名单（16 个路径）+ 黑名单（禁止写入项）结构，移除 shape 约束（shape 归属 outputGuide）

2. **`outputGuide`** — 从 13 行简略说明扩展为 70 行字段清单：
   - 为 `/presentation` 列出 5 个子字段（recommendationCategory 15 选 1、recommendation、recommendations 恰好 3 条、features、cover）
   - 为 `/itinerary` 列出每天 7 个子字段（day/title/spots/description/hotel/meals/mealDescriptions 恰好 3 个）
   - 为 `/commercial/terms` 列出强制 4 字段（inclusions/exclusions/bookingNotes/refundPolicy）
   - 为其余 13 个路径列明 value 类型和约束
   - 使用 ⚠️ 标记强调"缺任何一项都会被本地校验拒绝"

3. **`responseJsonSchema.value`** — 从 `{}` 增加 description，提示 function calling 层哪些路径的 value 是完整嵌套对象

4. **`systemPrompt`** — 从 7 行扩为 28 行：
   - 添加模块检查清单（9 个 ⬜ 必生成模块），解决"遗漏生成"问题
   - 添加文案风格参考（presentation/itinerary/terms 的 few-shot 示例）
   - 规则从约束优先改为主张优先（先说什么必须生成，再说不可虚构什么）

### 设计原理
- AI 的 function calling 层读到 `value: {}` 时认为 "value 可以是任何东西"，无结构化引导 → 给 value 加 description 指向 system prompt 中的详细清单
- 旧 prompt 大量文字说"不要虚构 X"，但没有说"presentation 必须包含 Y" → 改为每个路径先正列举必须字段，再附约束
- Patch 格式与"生成完整产品"的心智模型不匹配 → 添加模块检查清单和 few-shot 示例降低认知转换负担

### 验证
TypeScript 编译通过（tsc --noEmit 零错误）。测试文件不直接引用 prompt 字符串常量（只测 schema/parsing），不受影响。

## 新建项目后 AI 生成中的 Loading 状态

用户反馈：刚创建项目进入页面时，AI 应该正在生成，但右侧直接展示"5 项待处理"的报错列表，没有 Loading 提示。

**问题根因**：`review-summary.tsx` 渲染时只判断 `readiness.issues.length > 0`，并未判断 `loading` 状态。即便产品 JSON 是空的（`project.product` 是 `{}` 或 `null`），就绪度检查仍会列出 5 项缺失字段，让用户感觉"刚进来就看到一堆错误"。

### 改动
**`src/renderer/app/views/workspace/review-summary.tsx`**：
- 新增 `isGenerating = loading && isProductEmpty` 派生标志
- 顶部 `modeBarMeta` 的状态 pill：生成中显示"AI 正在生成…"（teal researching 状态），替代"X 项待处理"
- 顶部 hero 的就绪度数字：生成中显示"—"和"生成中"文字，进度条 width 走 0%
- 整个 scroll 区：当 `isGenerating` 时**替换为**一个新的 `generatingPane`：居中的 spinner + "AI 正在生成完整方案…" 大字 + 副标题，再下方 3 张骨架屏卡片（用 shimmer 动画）
- `showTaskFooter`/`showTaskHint` 在生成中也隐藏，避免底部出现空状态

**`src/renderer/app/views/workspace/review-summary.module.less`**：
- 新增 `.generatingPane` / `.generatingHero` / `.generatingSpinner` / `.generatingTitle` / `.generatingHint` / `.generatingSkeleton` / `.skelCard` / `.skelRow` / `.skelBar` + 5 种宽度变体
- 新增 `@keyframes ai-teal-spin`（spinner 旋转）、`@keyframes skel-shimmer`（骨架屏流光）
- 配色用 `--ai-teal` 软色（teal 6% 底 + teal 28% 边框），跟对话区"AI 正在生成回复…"视觉一致

### 关键判断
**何时算"生成中"状态什么时候不该隐藏正常内容**？
- `loading && isProductEmpty` → 完全替换为骨架屏（用户看到的"5 项待处理"全是空产品的虚假报错）
- `loading && !isProductEmpty` → 已有部分字段，仅切顶部 pill 颜色为 teal，不替换列表（用户能看到 AI 正在补齐的进度）
- `!loading` → 正常显示

### 验证
- `tsc --noEmit` (主) 零错误
- `tsc --noEmit -p tsconfig.renderer.json` 零错误（修过一次变量声明顺序错）
- `npx vite build` 成功，CSS 119KB / JS 330KB

### 经验
- **空产品状态 vs 真实错误**：就绪度检查对空产品仍然列出所有缺失字段，UI 必须区分"还没生成"和"生成后还有问题"。LoaderCircle 这种"AI 正在干活"视觉比堆列表项更能让用户安心。
- **CSS Modules + spinner**：本地 `@keyframes` 直接放在使用它的模块里（不必抽到 shared），shimmer 动画也是。两套 keyframe 互不干扰。
- **teal 偏色**：用 `color-mix(in srgb, var(--ai-teal) 6%, var(--surface))` 调"软背景"是仓库既定模式（操作日志卡片也用），比手写 hex 更易随主题切换。

## AI 首轮生成后自动补齐缺失模块

用户测试优化后的提示词，AI 返回的 JSON 仍然缺失 presentation、itinerary、commercial 子模块（pricing/inventory/release/terms）。

### 根因
提示词优化方向正确——basicInfo（subtitle、province、operationNotes）和 operations 全字段现在都能生成，提示词没白改。**瓶颈从"AI 不知道字段怎么填"变成了"AI 在一次调用里产出疲劳"**：8-9 个复杂嵌套模块一次性生成 + 转 patch 格式，认知负载太高。AI 倾向选容易的（basicInfo string/number 字段）写 40-50% 就停，不继续出 presentation/itinerary 的大段 JSON。

### 改动
**`src/main/main.ts`** — 新增 `detectMissingModules()` 函数 + 首轮生成后的自动补齐逻辑：

```typescript
detectMissingModules(product):
  检查 presentation（对象不存在）、itinerary（数组为空）、
  commercial/pricing、commercial/inventory、commercial/release、commercial/terms 是否已写入

runAiReply 中首轮成功后（isInitialDraft=true）：
  → 如果缺失模块 > 0，拼接 followUpMsg = "以下模块尚未生成：presentation、itinerary..."
  → 追加一轮 service.reply()，专门补齐缺失模块
  → 补齐失败不抛错（第一轮产物已可用，用户还能持续对话补齐）
  → 第二轮 researchTasks 也合并入 DB
```

### 改动

**1. `minimax-constants.ts` — 提示词新增"直接生成边界"**
- 规则 3：价格/库存/条款/封面图必须直接写 product JSON，不得用 researchTask 代替

**2. `main.ts` — AI 生成后自动补齐车辆/酒店资源**

**3. `vehicle-resource.ts` — 加价格过滤的车辆资源匹配**

### 预期效果
- 之前：5 条核查任务（含车辆、酒店、价格、库存、条款）
- 之后：AI 直接生成价格/条款/封面 + 代码自动补齐车辆/酒店 → 预计只剩 0-2 条需人工核查

### 验证
- `tsc --noEmit` 主 + renderer 零错误
- `npx vite build` 成功

### 设计理由
- **不改变模型行为，只加兜底**：如果 AI 第一轮就生成全了，`detectMissingModules` 返回空，无额外开销
- **只补关键模块，不浪费 token**：basicInfo/operations 通常第一轮就齐了（因为它们字段浅），第二轮只需要补 presentation + itinerary + commercial 子模块，专注度更高
- **失败不阻塞**：补齐失败 ≠ 整个生成失败，用户看到的仍然是"部分生成 + 可继续对话补齐"，比之前没有任何产物强

## VBK 多账号登录支持

用户需求：VBK 登录要支持多个账号。新增登录时把当前浏览器里的登录态清除（清除前保存到其他地方），下次再登录时取回，并且新增登录时右侧打开 WebView 显示 VBK 登录页。

### 方案
采用 **cookies 持久化 + 单会话切换** 模式，不引入多 partition：
- 当前活动的 VBK 账号仍然写在 `persist:vbk` Electron partition 里（活动态）
- 每个账号的 cookies 数组（来自 `session.cookies.get({})`）写到 SQLite `login_sessions` 表
- 切换 = 先 `get({})` 当前 cookies 落 DB → 逐条 `cookies.remove()` 清空 → 逐条 `cookies.set()` 回灌目标 → flushStore → loadURL
- 新增 = 先 saveCurrentSession（如果当前已登录）→ 清空 → 导航到 VBK 根目录让用户重登

### 改动文件

1. **`src/main/infrastructure/database/database.ts`**
   - 新表 `login_sessions (account_key, account_name, cookies_json, saved_at)`
   - `saveSession(key, name, cookiesJson)`：upsert + 空 cookies 等同删除
   - `loadSession(key)` / `listSessions()` 按 saved_at DESC / `deleteSession(key)`
   - 同时 `deleteSetting(key)` 公开，让 `vbkActiveAccountKey` 能干净清除

### 关键设计决策

- **不用多 Electron partition**：原 `persist:vbk` 是单个 partition；改多 partition 需要为每个账号维护独立 WebContentsView + 大量边界条件。Cookie 备份/恢复简单可靠，能覆盖 VBK 的登录态（cookie 主导）。
- **cookies.set 需要 url**：Electron 的 `cookies.set` 必须传 scheme+host，所以从 cookie.domain（可能带前导点 `".ctrip.com"`）+ secure 派生 url
- **active key 单独放 settings**：`vbkActiveAccountKey` 区别于 `vbkAccountName`：前者用来 switchAccount 定位 cookies 表行；后者用于 providerId 缓存和 UI 头像
- **登录中 fire-and-forget save**：检测到登录后立刻异步落快照，不阻塞 status 返回。期间 cookies 可能尚未全部写入 session（多次 set），下次 checkVbkLogin 会自然覆盖
- **删除当前账号拒绝**：避免一个已"忘记"的账号立刻被加进活跃指针再复活，"忘记"语义干净
- **空 cookies 等同删除**：saveSession 收到 `[]` 或空串会自动走删除路径，防止把"空白账号"误当成"已记录"

### 经验

- **Electron Cookie 的 url 字段**：`session.cookies.get({})` 返回的 Cookie 不含 url（仅 domain/path）；必须从 domain 构造 "https://host" 才能喂给 `cookies.remove(url, name)`
- **remember: who-the-cookies-belong-to**：cookie 表的 key 用 loginAccount（如 vbk_671205）而非 displayName，避免同一身份证的 "vbk_xxx" 和 "小璐" 在不同 set 设备下被视为不同账号
- **status 与 save 解耦**：vbkLogin（探测）vs vbkLoginAccounts（DB 真相）应走两条独立的拉取链路 —— 让"刷新账号列表"不再被网络卡住
- **典型陷阱**：clearStorageData 之外还要单独 `cookies.remove`，否则分区级的 cookies 缓存可能在 session 重建后又跑回来
