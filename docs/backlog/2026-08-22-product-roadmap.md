# VBK Desktop 后续产品立项与待办

> 记录日期：2026-08-22
> 目标：把当前明确要做、以及从现有代码链路中暴露出的可优化项，沉淀为后续继续推进的产品 backlog。

## 背景

当前主路径已经能围绕「私家团」生成结构化产品、规划行程、补齐资源、保存 VBK 草稿。下一阶段重点不是单点修 bug，而是把产品能力从单一私家团扩到多团态，并提升运营在图文、酒店、封面候选和人工复核上的控制力。

## P0 立项

### 1. 支持多团态：自由行、半自助

现状：
- 新建产品 UI 目前只开放「私家团 / 跟团游」。
- `CreateProductInput`、IPC 校验、planning skeleton 仍把产品形态收窄到 `privateTour | groupTour`。
- VBK 自动化常量里已经有 `freeTravel`、`semiSelfGuided` 的中文映射，但 sale-control 创建页当前会把非跟团游都回退成私家团。
- 私家团用车资源阶段只对 `privateTour` 生效；自由行、半自助需要明确跳过、改用别的资源策略，或进入人工复核。

目标：
- 新建产品支持选择「自由行」「半自助」。
- 产品 skeleton、planning prompt、schema、数据库初始化、远端产品创建接口和 review 展示统一识别四类形态。
- 自动化 sale-control 能按真实形态选择 VBK 的产品形态，不再静默回退私家团。
- 不同形态拥有清晰的资源策略：私家团配置用车资源，自由行/半自助默认不要求私家团资源组；半自助是否需要局部用车，应在规划输出和 readiness 中单独表达。

建议拆分：
1. 产品形态枚举统一：shared contracts、IPC 输入校验、product draft、planning skeleton、review 展示。
2. 创建页与产品列表展示：新建下拉、产品标题/包名中文标签、历史数据兼容。
3. planning 规则：不同形态对应的行程密度、酒店、交通、卖点文案策略。
4. VBK sale-control 实测：确认当前账号/合同下自由行和半自助可选项、文案和锁定状态。
5. 自动化阶段矩阵：明确每个形态是否执行 vehicleResource、hotelResource、package、terms、preflight。

验收门：
- 四类形态都能创建本地产品，并在产品详情中显示正确中文形态。
- 自由行、半自助不会被本地 draft 或 VBK 创建阶段改写成私家团。
- 私家团仍触发用车资源任务；非私家团不会出现“私家团资源组缺失”的阻塞。
- 至少完成一次自由行、一次半自助的真实 VBK 草稿创建和 sale-control 回读。

### 2. 酒店自动录入闭环

现状：
- 已有 `ensureHotelResource`，能按 `operations.hotelTier` 和行程住宿判断进入资源配置。
- 代码已处理“独立酒店入口”和“套餐资源承载住宿”两条路径。
- 仍缺少稳定的产品级闭环：规划阶段的酒店选择、资源匹配、自动录入结果、失败后的运营复核入口还没有形成一套可感知流程。

目标：
- 行程含住宿时，酒店来源、酒店档次、住宿晚数和资源配置策略完整可见。
- 自动化能优先使用 VBK 可匹配资源；找不到时明确进入非平台酒店或人工复核，不假装成功。
- 保存草稿后能回读酒店资源配置或套餐承载证据，给运营看到“已配置 / 套餐承载 / 待处理”的结果。

建议拆分：
1. 规划阶段强化：酒店描述、酒店档次、住宿晚数、自由行/半自助差异。
2. 资源解析阶段：把 hotelResource 查询结果和 fallback 原因写入可展示证据。
3. 自动化回读：酒店资源页保存后读取实际配置，避免只凭点击结果判成功。
4. UI 复核：在基础信息或运营复核中展示酒店档次、资源状态、套餐承载状态、失败原因。

验收门：
- 含住宿产品能在保存草稿流程中自动处理酒店资源阶段。
- 无独立酒店入口但套餐承载住宿时，状态展示为“套餐承载”，不写伪酒店资源。
- 钻级不一致时必须停止并给出可操作提示。
- 至少用一个真实含住宿产品完成 VBK 页面/API 回读验证。

### 3. 副标题、推荐语、卖点文案优化

现状：
- `basicInfo.subtitle` 已进入 planning schema 和基础信息自动录入。
- `presentation.recommendation`、`presentation.recommendations`、`presentation.features` 已有结构和富文本安全归一化。
- 推荐理由分类已经统一到九个 VBK 类目；但副标题格式和卖点表达还没有按运营口径做精修模板。

目标：
- 建立可复用的副标题格式：目的地、天数、形态、核心体验、服务边界清楚，不堆砌。
- 建立卖点生成规范：推荐语、三条推荐理由、产品特色富文本各司其职，避免重复。
- 按产品形态差异输出文案：私家团强调专属服务，自由行强调灵活度，半自助强调核心段托管与自由时间。

建议拆分：
1. 副标题模板：长度、标点、禁用词、信息顺序、不同形态样例。
2. 卖点模板：`recommendation` 一句话、`recommendations` 三条分类理由、`features` 富文本 3-5 条。
3. 黑名单和敏感词重写：沿用当前 presentation sensitive rewrite，但增加副标题格式校验。
4. UI 人工重生成：保留单字段重生成入口，让运营可以只优化副标题或卖点。

验收门：
- 副标题不为空，长度和格式稳定，真实写入 VBK `baseInfo.subName` 后回读一致。
- 卖点富文本只含允许标签，且三条推荐理由分类不重复、都在九类白名单内。
- 文案不出现不符合产品形态的承诺，例如自由行写成全程专车专导。

### 4. 多封面候选与运营手动挑选

现状：
- 产品当前只保存一个 `presentation.cover`。
- 携程图库候选查询和手动上传已有基础链路，UI 可以选择一张具体图。
- 自动化 readiness 对手动上传封面仍有阻断；VBK 图库封面需要 `imageId` 和 `imageUrl`。

目标：
- 规划/封面搜索阶段生成多张候选封面，而不是只保留一个最终封面。
- 运营可以在候选池中预览、选择、删除不需要的图。
- 最终保存草稿时只使用运营选中的主封面；候选池作为本地证据和备选保留。

建议拆分：
1. 数据结构：新增 coverCandidates 或 coverGallery，保存候选图来源、imageId、imageUrl、分辨率、score、POI、状态。
2. UI：封面候选列表、主封面标记、删除候选、重新搜索、手动上传并入候选池。
3. 自动化：只消费 selected cover；未选主封面时 readiness 阻断。
4. 清理策略：删除候选时释放手动上传文件引用；避免本地 covers 目录孤岛文件。

验收门：
- 同一产品可以保留多张封面候选，并明确一个主封面。
- 删除候选不会误删当前主封面，也不会留下无引用的手动上传文件。
- VBK 保存阶段只绑定主封面，保存后能回读确认 imageId。

## P1 可优化项

### 5. 产品形态与阶段矩阵可视化

为每个产品显示“该形态会跑哪些阶段、哪些阶段被跳过、为什么跳过”。这样自由行/半自助上线后，运营不会把合理跳过误判成失败。

验收门：保存草稿前的 readiness 能显示阶段矩阵；跳过项必须有原因，例如“自由行不需要私家团用车资源组”。

### 6. 规划失败和重做阶段的可见诊断

最近已有单阶段重跑入口，但仍需要真实 Electron/VBK 环境复现和更直观的错误反馈。后续可把 planning 阶段失败原因、最后一次模型输出摘要、可重做模块放到同一处。

验收门：任一 planning 阶段失败后，运营能看到失败阶段、失败原因、可执行动作；重跑成功后旧阻塞状态消失。

### 7. 远端产品与本地状态一致性提示

产品列表/详情以远端 Tibet 为权威，本地 SQLite 是运行态。后续可以在 UI 上更明确地区分“远端产品状态”和“本地自动化状态”，减少误解。

验收门：产品详情能同时展示远端状态、本地 planning 状态、VBK 草稿状态；任一状态过期时提示刷新。

### 8. 运营复核字段的批量确认

当前很多字段可以单独人工调整。后续可以增加“复核完成”视图，把价格、库存、酒店、车辆、封面、卖点、条款集中成一个 checklist，减少来回找字段。

验收门：保存草稿前可一屏看到所有必须复核项；缺失项点击后能定位到对应编辑区域。

### 9. 封面/POI/资源任务的证据归档

研究任务已经能记录待办和部分证据。后续可把封面候选、POI 选择、酒店资源、车辆资源的来源、时间、选择人和回读结果统一归档，便于复盘。

验收门：每个关键运营字段都能看到“来源 / 最后更新时间 / 是否已被运营确认 / 平台回读结果”。

### 10. 真实 VBK 验收样例库

随着自由行、半自助加入，需要维护小样例库：每种形态至少一个短线、一个长线、一个含住宿、一个无住宿。样例用于回归测试和运营演示。

验收门：样例 JSON 能驱动规划和保存草稿；每个样例记录最后一次真实 VBK 验收日期、账号、结果和已知限制。

## 建议推进顺序

1. 先做产品形态枚举统一和 sale-control 实测，否则自由行/半自助会被底层回退成私家团。
2. 接着做阶段矩阵和 readiness，防止多形态后“跳过/失败/待人工”的语义混乱。
3. 再做酒店闭环，因为它跨 planning、资源查询、自动化、回读和 UI。
4. 然后做副标题/卖点模板，收益高、风险相对可控。
5. 最后做多封面候选池，因为它需要数据结构、UI、文件引用和自动化消费一起改。

## 开工前检查清单

- 先确认当前 VBK 账号和合同下，自由行、半自助在 sale-control 页面是否可选。
- 修改产品形态枚举时，要同步 shared contracts、IPC zod、数据库 draft、planning skeleton、automation schema、renderer review helpers。
- 所有涉及 VBK 保存的改动，不能只用单测证明完成；必须至少有页面/API 回读证据。
- 保持已有私家团路径不回退，尤其是车辆资源组、酒店资源、条款保存和 preflight。
