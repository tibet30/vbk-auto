## 必须先解决的一处冲突

"所有信息都能调整"与决定 A 在**产品数据**上直接冲突：

- 产品的「行程录入」是 `行程规划 → 程序检查 → 运营确认 → 行程录入` 的最后一环；
- 如果智能体凭一次通用授权就直接改 VBK 上的产品（标题、行程、价格、资源），等于**同时跳过**程序检查与运营确认；
- `AGENTS.md` 把这条状态机写成硬约束，且现有 5 项正向回归的终点正是"到达 VBK 录入前一步、停在 `waiting_approval`"，测试在这个终点之前不会拦下"通用授权直接改产品"的路径。

我的建议（**门禁保持，写入照做**）：

> 涉及产品数据的写动作必须绑定一个**已通过程序检查且已被运营确认**的产品；通用授权只算"执行许可"，不算产品确认。非产品类（账号/供应商资料等）不涉及产品门禁，按通用授权直接执行。

这样"账号权限内都能调整"仍然成立，只是产品数据的调整必须发生在产品自身门禁之后，而不是绕过它。

## 动作清单（按建议顺序）

全部遵循：受 Zod/JSON Schema 约束 → `preview` 展示将发送的真实内容 → 授权 → 同账号串行执行 → `reconcile` 回读核对 → 收据。后台写准入守卫（`assertBackendWritesAreVerifiable`）会拒绝缺 `preview`/`reconcile` 的动作。

| # | 动作 | kind | 前置读取 | 执行后核查 | 风险 |
| --- | --- | --- | --- | --- | --- |
| 1 | `vbk.basicInfo.field` 改单个基本信息字段（400 电话、管家联系人等） | write | 读当前值并进 preview 做 diff | 回读该字段确认新值 | 低（可改回） |
| 2 | `vbk.resource.bind` 绑定资源（车型/酒店规则/票种） | write | 读当前绑定列表 | 回读绑定列表含新项 | 中（影响可售） |
| 3 | `vbk.presentation.cover` 更换封面（图库选图或指定图） | write | 读当前封面 | 回读封面 id | 中 |
| 4 | `vbk.sale.publish` 发布/上下架 | write | 读当前售卖状态 | 回读状态位 | 高（对外可见，建议最后做） |

不建议先做"删除类"与"提交审核类"：不可逆且触及平台审核流程。

## 实施步骤（建议按此顺序）

1. **打通写链路（不碰真实数据）**：以动作 1 为样板，用端口注入 + fake 适配器实现完整链路（plan → 授权 → 串行执行 → 回读 → 收据 → uncertain 收敛），补齐单测与负向用例。
2. **真实只读核对**：对目标账号读一次当前基本信息，确认 preview 里展示的就是平台上真实的值。
3. **一次受控真实写**：由你在场确认的一次字段级修改（可改回），验证回读与收据，并确认不影响 25 项强制回归。
4. **按清单逐条扩**：每条动作单独走 1–3 的流程，一条一个提交范围。

## 验收门

- 单测：每个写动作必须有"缺 preview/reconcile 被拒装配"、"审批前外部无变化"、"幂等键重复提交只写一次"、"回读不一致落 uncertain"四类用例；
- 真实后台：只读核对通过 → 一次受控真实写 → 回读一致；
- 回归：`npm run test:changed` 必须仍为 5 项正向 + 20 项负向全部通过（写动作不得改变产品门禁的判定）；
- 行数与类型：所有新增文件 ≤350 行，`tsc` 双工程 0 错误。

## 决策已定：A（2026-11-17）

运营选择 **A**：允许智能体修改产品数据，但**必须先通过该产品自身的程序检查与运营确认**；写动作携带确认凭据；非产品类不涉及产品门禁。

已落地：
- 门禁 `VbkWritePort.gate()`：本地产品存在 → 已回填 VBK 产品 id → `readiness.ready`（程序检查）→ `itinerary review status=verified` 且有 `approvalId`（运营确认）。任一不满足即拒绝，并说明缺什么。
- 第一个动作 `vbk.product.basicInfo`（skill `vbk-write`）：把本地产品基本信息写入 VBK，复用 `ensureBasicInfoApi` / `getProductBaseInfoApi`。
  - 目标键 `vbk:product:<vbkProductId>`，账号键取**运营确认记录里的 accountKey**，因此写操作按真实后台账号串行；
  - 审批卡展示标题/集合城市/天数/400 电话/管家联系人 + 确认凭据；
  - **执行前回读 VBK 当前值写进收据 `before`**（前置状态），执行后回读标题比对，一致才算落地；
  - 账号未配置管家联系人卡或 400 电话时直接拒绝写入，不静默降级。
- 后台写准入守卫（`assertBackendWritesAreVerifiable`）已覆盖该技能：缺 `preview` 或 `reconcile` 无法装配。
- **执行期复检**：门禁不只在"提出动作"时判一次。批准、执行前都会重新解析目标并重跑门禁——若产品在批准后被改回未通过状态，执行阶段直接拒绝，不会写入。已用真实数据库 + 真实门禁适配器验证（`test/agent/vbk-write-gate.test.ts`）。

尚未做的：真实后端的一次受控写入（按计划第 3 步，需要你在场确认）；以及清单里第 2–4 项动作。
