# 行程规划与 VBK 录入稳定性治理执行方案

日期：2026 年 10 月 4 日。状态：诊断与规划完成；行程规划首轮实现及本地验证完成。真实应用验收、其余工作包和真实平台验收尚未开展。面向后续 Codex 执行器及产品验收人员。

目标是让产品从用户输入、行程规划、资源核验、正式确认到 VBK 未提审草稿形成可恢复的完整流程。第一优先级是减少简单问题的询问、避免同类问题反复卡住，并让已经掌握解决方法的故障自动恢复。遇到外部错误时，系统应自动完成有证据支持的恢复；确实需要人工处理时，明确说明原因、已完成内容和下一步，避免长期停在“处理中”或反复要求“继续”。

当前项目已经具备 Agent 完成门、正式审批、确定性录入、阶段回读和部分恢复能力。实施应补齐这些能力之间的契约，不重写整个系统。优先处理工具停滞、写入结果不确定、阶段版本不一致和真实验收覆盖不足。

配套文档：[调查证据](./2026-10-04-planning-vbk-reliability-evidence.md)、[验收矩阵](./2026-10-04-planning-vbk-reliability-acceptance.md)。三份文档共同构成执行边界。

用户随后明确优先解决行程规划，因此当前实施收窄为[行程规划首轮执行与验证](./2026-10-04-itinerary-planning-first-pass.md)。本轮处理结构节点排序、节点自动推进、生成结果回读、已满足问题续跑、无进展恢复预算与进度查询边界；录入账本、工具期限、流式存储和新的长期记忆系统仍未实施。下方六轮是完整治理路线，首轮修复不等于 R1 或全部 A01 至 A32 已通过。

## 当前事实与问题判断

2026 年 10 月 4 日只读采样：76 个产品，71 个为 `draft_saved`，4 个为 `blocked`，1 个为 `planning`。最新工作流有 70 个 `succeeded`。当前明确未保存的 5 个产品包括模型输入拒绝、行程阶段页面不可用，以及 3 个创建阶段权限回读失败。

这些是当前存量状态，不是首次成功率。原地更新、历史人工恢复、不同版本运行和日志截断会掩盖中途失败；不能用 71/76 宣称稳定性已经达标。5 个最新自动化虽然标为成功，交通阶段仍保留失败：3 个按当前资源规则可以降级，2 个属于保存或回读失败，仍需处理，不能一概当作成功或故障。

| 问题族 | 已确认的代码或记录 | 治理方向 |
| --- | --- | --- |
| 简单问题仍转交用户 | 已有默认答案和持久值复用，但主要匹配问题文字；`ask_user` 不受准备阶段动作门限制 | 提问前必须通过结构化决策门，自动执行可推导的下一步 |
| 同类故障反复卡住 | 已有专用修复，通用 Agent-controlled advisor 却默认 `wait_for_user` | 先调用明确的安全恢复器，回读成功后自动续接；同因共享预算 |
| 工具长期没有返回 | 业务 `tool.execute` 缺少统一执行期限；模型自身已有超时 | 工具生命周期、进度监测、取消和过期结果隔离 |
| AI 反复尝试却不推进 | 80 轮上限、相同参数失败熔断、无工具完成门均已有；改变参数或无实质进展的本地写仍可继续循环 | 以当前缺项和业务语义衡量进展，持久化阶段预算 |
| 长对话可能拖慢主进程 | 流式回复可每约 48ms 全量保存快照，随后更新工作流和产品诊断 | 分离流式展示与业务写入，先量化再优化存储 |
| 请求异常后结果不确定 | 兼容页面路径可在上下文丢失后重发请求；创建记录出现壳 ID 已返回但回读权限失败 | 区分查询与写入，先对账再决定恢复 |
| 已完成阶段与新方案不一致 | 阶段只有状态，没有输入语义指纹；恢复按 `completed` 跳过，确定性运行容忍方案指纹漂移 | 阶段输入与回读绑定，按依赖失效旧证据 |
| 完成与界面状态不一致 | 产品、Agent、workflow、automation 的状态投影存在多入口 | 统一按当前运行和业务证据投影，不覆盖历史终态 |
| 修复后仍可能再次卡住 | 唯一 live E2E 从预置 JSON 直接调用接口，未覆盖桌面创建和规划确认 | 补完整用户路径与新进程恢复验收 |

请求重发和方案漂移属于已确认代码条件下的风险，尚未证明已在线上造成重复产品或错误授权。流式存储的性能影响也需要测量，不能直接将它定为全部卡顿的根因。

## 本次范围与交付边界

覆盖现有桌面创建入口、Agent 规划工具、资源核验、确认后录入、阶段回读、断点恢复、运行状态展示，以及对应回归测试和执行文档。

保留既有业务规则：

- 行政地点使用平台短名；创建后的 `meetingCity` 锁定，`destinationCity` 与其一致。POI 等名称不按行政尾缀规则处理。
- 完整行程保留原顺序、天数、二选一关系和明确服务活动；不能为了通过校验删除真实景点、伪造 POI 或改变酒店价格。
- 产品类型决定适用资源阶段；跟团及半自助不绑定用车资源组。缺少逐景点配图属于可选提示，真实封面仍按现有草稿规则核验。
- 保留确认方案后的授权范围、账号隔离、同产品串行和未提审草稿边界。

不增加新模型供应商、云端调度服务或全新 Agent 框架。不扩展提审、上架、发布功能。本方案不授权重跑当前真实产品或修改其业务数据。

实施时保留所有无关脏改动；新增文件通常不超过 350 行，接近 400 行时评估拆分。提交、推送、部署、删除和真实平台写入仍遵守仓库显式授权规则。

## 目标流程与完成契约

```mermaid
flowchart LR
    A[用户输入与锁定约束] --> B[按当前缺项生成方案]
    B --> C[本地持久化与就绪检查]
    C --> D[正式确认方案及录入范围]
    D --> E[确定性执行适用阶段]
    E --> F[逐阶段独立回读]
    F --> G[最终预检与状态收敛]
    E --> H[结果不确定时只读对账]
    H --> F
    H --> I[明确阻塞与恢复动作]
```

本地规划完成表示方案已经持久化、当前必要缺项清零，可以展示正式确认卡；不得显示“VBK 已完成”。草稿录入完成要求：有平台产品 ID，本次必要阶段均具有对应方案版本的独立回读证据，最终预检通过，产品为 `draft_saved`，本轮工作流与 Agent 正确结束。

母产品草稿和交通子产品分别记录结果。平台确认无可售资源、且符合当前业务跳过规则的分支，记为有理由和证据的 `skipped`；明确要求但仍失败的分支，显示“母草稿已保存，交通待处理”，不能宣称全部需求完成。优先利用现有状态加结构化 outcome，不预先要求新增一个全局状态枚举。

### R0 固定基线与复现材料

记录 HEAD、任务涉及文件的内容指纹、应用版本、主进程构建标识和配置摘要，核实运行中的应用是否加载该版本。不得仅靠源码存在或构建文件时间认定修复已经生效。基线固定采用文件清单和指纹，无需提交整个脏工作区。

建立脱敏的只读诊断入口，联合查询产品、最新 workflow、当前 Agent run、最新 automation、操作日志和资源检查点。输出错误来源、首次错误、最后有效进展、已确认远端写入、是否需要对账、能否安全继续。

固化当前 5 个未保存样本和代表性已恢复案例；没有完整旧日志时注明缺失。修订 `docs/agent-loop.md` 与 `docs/vbk-api/contract.md` 中已过期的入口及协议描述，分别列当前源码、离线验证和真实运行证据。

涉及：`src/main/agent/creation-recovery-readonly.ts`、`src/main/infrastructure/database/parts/`、现有 `operation_log`、`docs/agent-loop.md`、`docs/vbk-api/contract.md`、`test/fixtures/`。

退出条件：每个拟修缺陷有可重复的输入、期望结果和失败断言；当前已修复但未实跑的功能明确标记“已有实现，待验收”。

### R1 自主推进与实质进展

先实施提问前的程序决策门，再接入期限及性能治理。所有 `ask_user`、普通文本“请回复继续”和恢复 `wait_for_user` 都受同一决策合同约束，不能仅增加提示词。提问需携带目标字段、当前缺项、已查证据、已尝试动作、决策影响及机器不能决定的原因。

决策顺序固定为：当前用户指令与锁定约束 → 当前产品已保存值和本次已回答问题 → 同用户同账号范围的显式偏好与账号配置 → 已验证的产品规则 → 有预算的自动查询或修复 → 必需业务决策。信息冲突按明确的优先级处理，不能让旧偏好覆盖新指令。只复用既有持久能力，不新增复杂长期记忆平台。

| 情况 | 程序应直接执行的动作 |
| --- | --- |
| 只问“继续下一阶段、是否重试、是否生成副标题或推荐理由” | 依据当前缺项执行既有生成或安全恢复动作，不创建 pendingInput |
| 已保存酒店、联系人、封面、价格或库存 | 核验适用范围并复用；不重复索要字段或图片 ID |
| 本地审核指导价尚未生成 | 按当前商业生成合同自动计算并标明依据，在最终方案中供审核；不把普通生成转为人工填价 |
| 已有唯一有效 POI、默认账号联系人或明确产品类型规则 | 用确定性证据采用结果；歧义仍存在才进入决策门 |
| 原方案二选一、纯服务节点或可选景点图片缺失 | 保留原意，按已有活动合同处理；图片记可选待办，继续主链 |
| 字段格式、推荐理由长度、已知非法词或资源候选技术失败 | 进入限定范围的校验、改写、重新查询和回读，不询问用户要不要修复 |
| 缺少会改变核心行程或资源承诺的信息，且无规则或授权可决定 | 合并提出一次真实业务问题，解释差异；答案落在本产品决策记录中 |
| 正式 VBK 写入尚未授权，或业务方案发生实质变化 | 展示正式确认卡；普通 ask_user 不能替代授权 |

现有“按问题文字正则猜答案、取第一个选项”应改为按字段和业务证据决定。已有用户选择必须优先，不能为了少问问题随便选酒店、POI或覆盖封面。问题去重键使用字段、决策类型和账号，答案有效性只比较其依赖字段的语义版本，不能依赖模型生成的 questionId或整份产品版本；换措辞、生成不相关模块或重启后仍复用已回答结果，相关事实改变时才失效。

优先修复三处具体停点：`core.ts` 中旧问题已被当前产品满足后仍暂停并要求继续；保留已上传封面的答案被标记为pause；普通阶段错误一律进入固定wait_for_user。问题全部机器消解后应补齐工具结果并自动调度下一步；封面规格由机器先检查，确实需要用户上传时才停。

对已知同类故障增加小型恢复策略注册表，按阶段、结构化错误码、产品类型、协议版本和前置证据匹配已有恢复器。顺序为诊断 → 限定修复 → 持久化 → 权威回读 → 自动回到下一未完成节点。不要只自动填写“重试”答案后再等模型决定；能够确定的下一步由程序推进。

每条恢复策略有适用条件、禁止触及字段、共享次数与耗时预算、成功回读条件和失败出口。恢复成功案例固化为代码策略与回归夹具；未知的模型建议不会自动晋升为通用规则。预算耗尽且原因是软件或协议缺陷时显示准确技术阻塞，不把“是否继续碰运气”包装成用户选择。用户只能提供事实的场景才提出问题。

机器等待与用户主动暂停分别记录。登录、资源准备或图片上传等机械前置条件满足后，程序核实账号、方案及原授权仍适用再自动恢复；用户主动暂停、废弃或撤销授权时保持原指令，不自动启动。未知写入即使环境恢复也先只读核对。

在 Agent 工具边界增加统一生命周期：开始、最后心跳、最后有效进展、执行期限、等待原因、取消标记及结束结果。查询、本地生成、批量录入分别配置期限；已有模型和接口超时继续保留，不能用一个固定总超时误杀长价格库存任务。

建议初始值：心跳 5 至 10 秒一次，连续 30 秒无进展显示明确等待原因；具体执行期限按基线耗时和工具类别设定。心跳不能刷新“有效进展”的时间。批量任务用已回读日期、住宿段或子产品节点计数，显示当前项和总量。

超时后首先停止派发下一步并隔离旧执行器。对支持取消的查询使用 AbortSignal；对已派发写入进入 R2 对账，不能仅用 `Promise.race` 超时后释放锁并启动第二次写。迟到结果不得覆盖新运行或用户修改。

增加持久化进展指纹：当前大阶段、当前节点、必要缺项集合、资源阻塞及相关业务语义版本。连续 3 次完成操作后指纹不前进，触发有限补救或明确暂停；换参数、更新诊断文案和无效本地写都不能重置预算。保留现有同参数失败熔断和 80 轮保护作为最后防线。

流式文本保留即时展示；持久化先节流到每秒不超过 1 至 2 次，并在稳定事件结束时保存。工具 dispatch、工具结果、审批和检查点必须立即可靠落盘。流式片段不再重写业务产品 JSON 或触发业务版本递增和远端产品镜像。

先测量最大快照、长对话和主线程延迟。节流后仍不达性能门时，再将事件日志与快照头拆分存储；迁移必须保留完整历史，不直接删除旧快照。

涉及：`src/main/agent/core-tools.ts`、`preparation-question-defaults.ts`、`pending-question-reconciliation.ts`、`preparation-action-guard.ts`、`core-loop.ts`、`core-snapshot.ts`、`types.ts`、`integration-setup.ts`、既有 memory/context 接入、`src/main/main.ts`、产品诊断及远端镜像接入点。新增决策与恢复小模块，不继续扩张大核心文件。

退出条件：机器可决定的问题不进入用户等待，已回答问题不重复出现，已知故障修复并回读后自动推进；真实业务决策和正式授权仍保留。注入永不返回工具、假进展循环和长流式响应后，任务均在明确期限内进入可解释状态；不重复派发写入，不丢工具及授权事件。

### R2 写入结果与恢复策略

按端点业务语义标记请求为查询、可证明幂等的写入或非幂等写入，不能按 HTTP POST 一概认定。未知端点默认采用保守写入策略。接口成功标准由各端点合同定义，覆盖 HTTP、Ack、业务错误、返回字段和独立回读；有些查询允许空列表，有些写入缺 ID 即失败，不能统一规定所有空数组都失败。

增加持久化操作记录，优先复用 automation/Agent 检查点；若现有结构无法保证原子写和查询，再增加小型本地表。至少保存 operationId、产品与账号、运行与审批、阶段及子项、输入语义指纹、派发状态、回执、回读结果和共享重试预算，不持久化凭据。

关键顺序：可靠保存 `prepared` → 保存 `dispatched` → 发请求 → 保存回执 → 独立回读 → 保存 `verified`。关键落盘失败必须停止后续写入，不能吞异常继续执行。操作 ID 只保证客户端去重，不假设平台提供幂等键，也不承诺网络层严格 exactly-once。

恢复时将操作分为：尚未派发、已验证、明确未写入、部分匹配、结果未知、内容冲突。只有尚未派发、可靠证明未写入或合同确认幂等的写入可以重试。部分匹配只补缺项；结果未知只读对账；内容冲突保留现场并明确阻塞。

| 错误来源 | 默认处置 |
| --- | --- |
| 模型 422 或结构校验拒绝 | 单独定位生成请求及字段，有限修正；不原样无限重试，不创建 VBK 壳 |
| 查询网络超时或限流 | 有预算的退避重试，等待原因与到期时间可见 |
| 写入后的断网、超时、上下文丢失 | 标结果不确定，禁止传输层或 Retry-After 直接重发；进入只读回读 |
| Ack Warning 非法文案 | 复用现有字段级修复，最多两轮共享预算，保护事实和资源，成功后回读 |
| `40010001` 等账号或资源权限问题 | 区分账号、产品来源页、businessContext、绑定不一致；只读核验后决定，禁止重建壳碰运气 |
| 方案缺少必需资源 | 有限替代检索，无法满足则给一次明确决定；不伪造库存或绑定 |
| 可选配图或页面展示同步失败 | 记录警告并继续，真实封面及写入回读门仍保留 |

当前桌面主链使用 `nativeOnly`，不能依据旧资料强行切回页面请求。先建立同账号、同来源、同 businessContext 的只读协议对照，核实权限差异；支持的传输方式按端点合同选择。真实平台协议探测需另行授权。首次创建无本地产品 ID 时，保留已返回壳 ID和供应商编号；可查证时对账，查证不了明确保持未知，不猜测 ID、不再创建第二个壳。

普通 API 阶段保持与页面导航解耦。兼容页面路径的写入 fallback 必须同样遵守派发与对账规则；手动封面上传仍使用必需交互页面。native 与页面响应的 Ack、空数据和来源诊断保持一致。

涉及：`src/main/infrastructure/vbk-session-request.ts`、`vbk-session-fetch-adapter.ts`、`vbk-request-page.ts`、`src/main/agent/core-tools.ts`、`integration-reconcile.ts`、`src/main/automation/recovery/` 及各阶段读写入口。

退出条件：服务端已保存但响应丢失、context-loss、Retry-After、权限回读失败均不会再次无证据发写；关键 checkpoint 失败后写入次数不再增长。

### R3 绑定阶段输入与回读证据

为每个适用阶段持久化 `phaseKey`、输入语义指纹、依赖证据版本、操作记录、独立回读摘要和结果。阶段查找使用名称及子项键，不依赖数组索引，兼容历史已删除或不适用的阶段。

恢复时逐项比较当前方案、审批及阶段证据。相同输入且证据仍适用时跳过；业务输入变化时，只失效受影响阶段与后续依赖。派生 ID 重映射、格式规范化与允许的字段级文案修复必须有明确 diff 记录，不用“自动化正在运行”放行任何指纹变化。

最少依赖包括：城市、天数和行程变化影响基础信息、行程、住宿布局和条款；酒店候选影响酒店资源及服务卡片；套餐计价影响价格库存；交通配置影响对应子产品；每个相关变化均影响最终预检。价格变化不得使不相关封面重复绑定。

审批保存不可变的已确认业务基线。账号、城市、天数、POI、酒店选择、套餐价格、产品类型或录入范围发生实质变化时，停止旧派发并重新确认受影响方案。原授权仍有效且只有已确认范围的安全恢复，不重复向用户申请授权。

扩展已有 `integration-reconcile` 的比较器。基础信息恢复不能仅比产品编号和供应商编号；需比该操作期望的字段。图文、行程、套餐、价格、条款、酒店、用车和交通分别返回完整匹配、缺失、部分匹配或冲突。

酒店按住宿槽位及候选内容恢复，允许平台 ID 重映射；每段回读后保存进度。价格库存按已回读日期与价格库存语义恢复。交通沿用子产品创建、关系、启用、阶段和最终回读检查点，禁止已有子产品再次创建。

涉及：`src/shared/contracts-types.ts`、`src/main/agent/integration-gates.ts`、`integration-guard.ts`、`core-handoff.ts`、`src/main/automation/automation.main/`、酒店资源、价格批次及交通阶段。

退出条件：新进程从部分写入处恢复，只补真正未完成的子项；改方案不会复用旧完成证据，派生变化不会无谓阻断原授权。

### R4 状态投影与运营恢复

建立一个共享的只读业务结果投影入口，供列表、详情、阶段卡、workflow 和诊断使用。输入明确区分产品草稿结果、当前 run、历史 run 与本次需求；展示“规划中”“等待确认”“正在录入”“正在核对”“需处理”“草稿已保存”及独立剩余事项。

显示当前步骤、最后有效进展、已完成项、剩余项、重试预算及明确等待原因。对需要人工处理的情况，只给当前唯一可执行的动作，例如重新登录、确认差异、补必要资源或恢复指定阶段；不让用户猜该点哪个“继续”。

`draft_saved` 与历史 failed/paused 的冲突应按当前运行证据处理，不能因为存在任何 Agent 快照就永久拒绝收敛，也不能因为有产品 ID就假定全部完成。用户废弃的 run 保留废弃终态；此前已保存的草稿继续独立显示，不能强行把废弃任务改为成功。

允许跳过的交通缺资源与技术失败分别展示。历史失败保留在日志，成功后的当前阻塞清除。旧阶段名、旧审批指纹和旧 checkpoint 采用只读兼容与受控迁移；不得自动启动未知写入。

涉及：`src/main/agent/integration-workflow.ts`、`src/main/infrastructure/database/parts/workflow-tasks.ts`、共享结果合同、`src/renderer/app/views/stage-nav/` 和工作区状态组件。仅做必要状态展示，保持现有 DESIGN.md 规范。

退出条件：产品、任务、Agent 和自动化各层的展示均能解释，等待授权与废弃不被当作故障；当前成功不残留旧阻塞。

### R5 从新建入口进行完整验收

保留现有 API live smoke，并新增桌面用户路径验收入口：真实输入 → 创建本地产品 → Agent 规划与核验 → 本地持久化 → 正式确认 → 适用阶段录入 → 独立远端回读 → 正常退出重启 → 本地和远端再次核对。

默认执行离线故障注入、真实组件浏览器测试及隔离 SQLite 恢复测试；它们不接触真实业务库。真实 VBK 验收在完成这些门控后，列出账号、测试产品、创建或恢复动作和草稿范围，取得显式授权再运行。不得人为破坏生产草稿制造故障。

初始主验收选两条不同输入的全新私家团，覆盖酒店、用车和每日服务卡片。每次修复后重新计数，必须连续两次不发生需要人工救场的完整成功。不同产品类型的实际使用路径分别验收；缺平台条件的类型明确为“待环境”，不扩大宣称。

旧产品续跑证明恢复能力，全新创建证明首次完整流程能力，两者分别记录。交通子产品若属于授权需求，必须另行通过其节点和最终回读；合理跳过记录原因，真实失败保留剩余项。

涉及：`test/e2e/`、`test/agent/`、`test/workflow/`、`test/resources/`、`test/infrastructure/`、`scripts/run-tests.mjs`。运行器必须清楚报告真实测试启用与跳过情况，并核验长流程 timeout；跳过不能算通过。

退出条件：A01 至 A32 按环境逐项出结果，本地和真实证据分别列示，连续两次完整新建成功，有启动版本和独立回读证据；完整明确输入过程中不出现“继续、重试、补普通生成字段”的额外提问。

## 实施门控与停止规则

每轮先新增能够暴露缺陷的回归，再做最小实施，独立审查 diff，运行相关单元、集成或浏览器测试和类型检查。主进程入口或构建链发生变化时进行构建，并在安全停点重新加载应用确认版本。无新变更或未解风险，不重复扩大测试。

每轮交付文件清单、原因、验证结果、剩余环境项和下一轮入口。新缺陷若同因且直接阻断当前门，纳入本轮；其他问题进入后续清单。禁止通过放宽必要字段、隐藏失败或直接改业务库状态让验收变绿。

若落盘不可用、账号改变、写入未知或远端内容冲突，停止派发新写入，保留已经保存的内容。停在明确可恢复状态是正确行为；长时间无说明的 running、重复创建和假完成都是验收失败。
